## 1. Инструкция по gh (мультиаккаунт: энтерпрайз + личный)

### 1.1 Можно ли иметь несколько аккаунтов сразу?

Да. `gh` штатно держит несколько аккаунтов на одном host (`github.com`)
одновременно. Отдельно «залогинить gh для проекта» не нужно — каждый репозиторий
определяется по своему `git remote`, а не по логину. Один вход покрывает все твои
репозитории сразу.

### 1.2 Что уже сделано

- `gh auth login` выполнен для энтерпрайзного аккаунта `ial_tbi`.

### 1.3 Шаги настройки (выполняешь ты — нужен браузер)

**Шаг 1. Добавить личный аккаунт `thindie`:**

```
gh auth login
```

- Выбираешь: `github.com` → **Log in with web browser** → в браузере заходишь как
  личный аккаунт **`thindie`**.
- Второй аккаунт добавится к уже существующему `ial_tbi`, не заменяя его.

**Шаг 2. Сделать `thindie` основным (primary):**

```
gh auth switch
```

- В списке выбираешь `thindie`.
- Зачем: команды `gh secret set` и `gh release` по умолчанию ходят от primary
  аккаунта. Релизим мы в `thindie/arkanzabel`, поэтому primary должен быть он.
- Для других (энтерпрайзных) репозиториев можно переключить обратно через
  `gh auth switch`.

**Шаг 3. Привязать токены к репозиториям:**

```
gh auth setup-git
```

- Настраивает credential-хелпер, чтобы **каждый remote использовал свой аккаунт**:
  пуш тега в `thindie/arkanzabel` пойдёт под `thindie`, а работа с энтерпрайз-репами
  — под `ial_tbi`. Критично, чтобы пуши не ломались при двух аккаунтах.

### 1.4 Проверка

```
gh auth status        # показывает активный аккаунт и скоупы токена
gh api repos/thindie/arkanzabel --jq '.owner.login + " | role: ' + (.permissions.admin|tostring) + "/" + (.permissions.push|tostring)'
```

Ожидаемо: владелец `thindie`, и у него `push/admin = true`. Если всё ещё `false` —
значит `thindie` не primary или ему не выдан write-доступ (см. 1.5).

### 1.5 Нюансы и возможные проблемы

- **Доступ vs логин.** Даже залогиненный аккаунт имеет доступ только до того
  уровня ролей, что выдан в репозитории. Если `thindie` — владелец, у него полный
  доступ. Если ты работаешь под другим именем, а репозиторий на `thindie`, добавь
  этот аккаунт коллаборатором с ролью **Write**:
  Settings → Collaborators → add collaborator → `<login>` → роль **Write**.
- **Primary vs git-пуши.** `gh auth setup-git`路由ит пуши/пул по владельцу remote
  независимо от primary. Primary влияет только на gh-API команды (`secret`,
  `release`). Поэтому можно смело держать `thindie` primary и не бояться за работу
  с другими репами через git.
- **Протокол.** Remote у репозитория HTTPS; `setup-git` настроит токен именно для
  HTTPS. Для gh-API команд это не важно (они идут по API).
- **Выход из одного аккаунта** (если понадобится): `gh auth logout --github.com`.
  Это удаляет только выбранный аккаунт, второй остаётся.

## 2. Что нужно доделать перед публичным релизом (checklist)

### 2.1 Лицензионное соответствие GPLv3 (copyleft) — критично

В `docs/COMPLIANCE.md` прямо указано: файлы атрибуции из v2rayNG
(`open_source_licenses.html`, `licenses.xml`) **ещё не скопированы** в репозиторий
(фаза 0). Для публичного APK это обязательное условие лицензии.

- [ ] Положить текст **GPLv3** как `LICENSE` в корень репозитория.
- [ ] Запаковать список третьих сторон: `open_source_licenses.html` + `licenses.xml`
      (из v2rayNG) или сделать в приложении экран «Open source licenses».
- [ ] Обеспечить видимые «Appropriate Legal Notices» в UI (требование GPLv3 §7).
- [ ] Сохранить способность предоставить соответствующий исходный код GPL-частей
      (репозиторий открытый — условие уже выполняется).

> Без этого раздавать APK нельзя — это условие лицензии, а не формальность.

### 2.2 Движок / имя пакета — технический подводный камень

- `applicationId = com.thindie.rknzbl`, но `libhev-socks5-tunnel.so` собирается с
  `-DPKGNAME=com/v2ray/ang/service`, и JNI регистрируется на
  `com.v2ray.ang.service.TProxyService`.
- Если в сборке используется путь hev-socks5-tunnel, то смена пакета **без
  переборки** сомки ломает туннель.

- [ ] Проверить, собирается ли hevtun в текущей сборке (`compile-hevtun.sh`).
- [ ] Если да — перезобрать `.so` под твой пакет `com.thindie.rknzbl`, либо
      убедиться, что этот путь не используется.

### 2.3 Подпись сборки

- [ ] Сгенерировать release-keystore (не коммитить! — уже в `.gitignore`).
- [ ] Хранить keystore и пароли только в секретах GitHub.

## 3. Как релизить, когда всё будет готово

1. Задать секреты репозитория (нужен primary = `thindie`, write-доступ):
   ```
   gh secret set ANDROID_KEYSTORE_B64    --file ./keystore.b64
   gh secret set ANDROID_KEYSTORE_PASS   --value "..."
   gh secret set ANDROID_KEY_ALIAS       --value "..."
   gh secret set ANDROID_KEY_PASS        --value "..."
   ```
   (можно через web UI: Settings → Secrets and variables → Actions.)
2. Поставить тег на нужную ветку и запушить:
   ```
   git tag v1.0.0
   git push origin v1.0.0
   ```
3. Смотреть run в вкладке **Actions**; готовый APK появится в **Releases**.
